

## 一、核心概念与目标

### 1. 什么是拥塞控制？

TCP 拥塞控制是为了解决“**网络中间设备（路由器、交换机）处理不过来**”而设计的自动流量调节机制。它相当于 TCP 的“自动油门”，通过感知网络是否拥堵，动态调整发送数据的速度，避免把网络“堵死”。

### 2. 核心变量：拥塞窗口（cwnd）

- 发送方能发送的数据量 = **min(接收方通告窗口 rwnd, 拥塞窗口 cwnd)**。
- `cwnd` 完全由操作系统内核根据网络状况动态调整，应用层无法直接修改。

### 3. 拥塞控制 vs 流量控制

| 维度 | **拥塞控制** | **流量控制** |
| :--- | :--- | :--- |
| **关注对象** | **网络**（路由器、链路带宽） | **接收端**（应用程序处理速度） |
| **核心变量** | **拥塞窗口（cwnd）** | **接收窗口（rwnd）** |
| **最终窗口** | 发送窗口 = min(cwnd, rwnd) | |
| **本质** | 全局性的“路况探测” | 端到端的“匹配生产消费速度” |
| **解决** | 防止网络瘫痪（丢包、重传风暴） | 防止接收端缓冲区溢出 |


## 二、TCP 拥塞控制的四大核心算法

标准的 TCP 拥塞控制（基于 Reno/NewReno）由以下四个阶段循环组成：

| 阶段 | 触发条件 | 核心行为 | 增长速度 | 目的 |
| :--- | :--- | :--- | :--- | :--- |
| **1. 慢启动** | 连接建立时 / 超时重传后 | cwnd 从 1 个 MSS 开始，**每收到一个 ACK，cwnd 翻倍**（指数增长） | **极快**（指数级） | 快速探测网络可用带宽的上限 |
| **2. 拥塞避免** | cwnd 达到 **慢启动阈值（ssthresh）** | cwnd **每经过一个 RTT 增加 1 个 MSS**（线性增长） | **平缓**（线性） | 在接近带宽极限时谨慎试探，防止拥塞 |
| **3. 快速重传** | 收到 **3 个重复的 ACK**（Dup-ACK） | 立即重传丢失的数据包，**无需等待超时** | N/A | 提高丢包恢复效率（基于反馈，而非等待） |
| **4. 快速恢复** | 快速重传发生后 | 将 ssthresh 减半，cwnd 设为 ssthresh + 3，然后线性增长 | 平缓 | 避免进入慢启动，保持较高吞吐量 |

> **关键标志**：**ssthresh（慢启动阈值）** 是动态调整的“减速线”。当发生丢包时，ssthresh 会被设置为当前 cwnd 的一半。


## 三、CUBIC 算法深度解析（现代默认算法）

CUBIC 是目前互联网上应用最广泛的算法（Linux、Windows、macOS 默认），专为解决传统算法在**高带宽、高延迟**网络中的性能瓶颈而设计。

### 1. 核心公式

> **W_cubic(t) = C * (t - K)³ + W_max**

| 参数 | 含义 | 作用 |
| :--- | :--- | :--- |
| **W_max** | 上一次发生拥塞时的窗口大小 | 算法的“锚点”，记录丢包时的位置 |
| **t** | 从上一次窗口减少开始计算的时间 | 控制恢复速度 |
| **C** | 常量 | 控制算法的“进攻性”，值越大增长越快 |
| **K** | 从当前窗口增长到 W_max 所需的时间 | 决定拐点位置 |

### 2. 三种运行模式

| 模式 | 触发条件 | 行为 | 特点 |
| :--- | :--- | :--- | :--- |
| **TCP 友好模式** | 计算出的窗口小于标准 Reno 的窗口 | 采用 Reno 的线性增长 | 确保在低带宽网络中与 Reno 公平竞争 |
| **凹区域（Concave）** | cwnd < W_max（丢包恢复期） | 窗口快速增长，迅速回升 | 快速“弹回”到丢包前的水平，高效利用带宽 |
| **凸区域（Convex）** | cwnd > W_max（新领域探测） | 窗口缓慢增长，小心试探 | 谨慎探索是否还有更多可用带宽 |

### 3. 与经典 Reno 的对比（为什么 CUBIC 更强）

| 特性 | 经典 Reno | CUBIC |
| :--- | :--- | :--- |
| **窗口增长函数** | **线性**（每 RTT 加 1） | **三次函数**（y = x³ 曲线） |
| **拥塞退让幅度** | 窗口减半（β = 0.5） | 窗口减少至 W_max * 0.7（β = 0.7） |
| **RTT 公平性** | **RTT 依赖**：RTT 越短，ACK 返回越快，窗口增长越快 | **RTT 友好**：窗口增长与 RTT 基本无关 |
| **设计目标** | 公平性 | 高 BDP 网络中的**可扩展性**和**稳定性** |

### 4. 生活案例：高速开车找限速

- **Reno（老司机匀速爬）**：限速 500 码，它从 0 开始，1 码 1 码匀速往上加。撞墙（丢包）后，直接退到 250 码，再继续龟速往上加。在高带宽下恢复极慢，浪费大量带宽。
- **CUBIC（新司机弹射起步）**：
  1. **记忆**：猛冲到 500 码时被交警抓了，立刻在导航里标记“前方 500 码是极限（记录 W_max）”。
  2. **快速恢复**：不像 Reno 缩回 250 码，而是**只降到 350 码（降 30%）**，然后**一弹射加速**冲回 490 码。
  3. **谨慎试探**：超过 500 码后，松开油门极其缓慢地试探，看限速有没有提高到 510 码（凸函数探测）。

> **灵魂总结**：CUBIC 的轨迹就像数学里的 **y = x³（三次函数）**——**离上次堵车点越远，加速越快；离上次堵车点越近，减速越慢**。收放自如，效率拉满。


## 四、TCP 层的“感知”与“认知”（灵魂拷问）

**核心结论**：TCP 层有“感知”（传感器），但没有“认知”（思想）。它像一个精密的定速巡航系统，能测量车速，但不知道为什么要这么开。

### 1. TCP 能“感知”到什么？（输入信号）

| 信号 | 感知方式 | 代表含义 |
| :--- | :--- | :--- |
| **丢包** | 收到 **3 个重复 ACK** | 轻微拥塞（路上有个坑） |
| **超时** | **RTO（重传超时）** 未收到 ACK | 严重拥塞或断连（前面塌方了） |
| **延迟变化** | 计算 **RTT（往返时间）** | RTT 变大说明队列变长，开始堵车 |
| **速率反馈** | ACK 到达频率 | ACK 回来得快说明链路空闲，反之拥堵 |

### 2. TCP 永远“不感知”什么？（认知盲区）

- **不知道“为什么”丢包**：TCP 没有摄像头，分不清是路由器队列满了（真拥塞）、Wi-Fi 干扰（误码）还是网线松了。**它统一认定：只要丢包就是拥塞**（保守且安全的前提）。
- **不知道“前方”拓扑**：TCP 不知道自己在走千兆光纤还是 4G 弱网，看不见其他流在抢带宽。
- **无法预测未来**：只根据过去几毫秒的反馈做决定，没有宏观规划。
- **算法不切换**：TCP 自身**绝不会**主动切换拥塞算法。切换是管理员（root）通过 `sysctl` 强制执行的，TCP 只是机械地跑公式。

### 3. 直观类比：骑蒙眼赛马

- **马的感官（TCP 感知）**：马能感觉到脚下的路是硬是软（RTT 变化），能感觉到跑快了会不会绊倒（丢包）。
- **马的大脑（TCP 认知）**：马只有一套反射弧——路颠了就慢点，路平了就快点。它**完全不看地图**。
- **真正的决策者**：决定马是“匀速小跑”（Reno）还是“弹射起步”（CUBIC）的，是骑手（系统管理员）在出发前给马换的**马掌（内核模块）**。


## 五、常见问题与生产排查

### 1. 拥塞控制等于动态调整 MTU 吗？

**不等于。** 这是两个完全独立的机制：

| 维度 | **拥塞控制** | **MTU / MSS 调整** |
| :--- | :--- | :--- |
| **调控对象** | **拥塞窗口（cwnd）**：单位时间内发多少个包 | **最大分段大小（MSS）**：单个包能装多少数据 |
| **调控机制** | 动态调整**发送速率**（慢启动、快速恢复） | 由**路径 MTU 发现（PMTUD）** 触发 |
| **触发条件** | 检测到**丢包**或 **RTT 增加** | 收到 ICMP 的“需要分片但 DF 置位”差错报文 |
| **更改频率** | **毫秒/微秒级**（每个 RTT 都在变） | **极低**（仅网络拓扑变化时） |

**联动关系**：MSS 变了会影响 cwnd 的计数单位（字节数变化），但拥塞控制不会主动去改 MSS。

### 2. 如何查看当前系统的拥塞控制算法？

libash
# 查看当前系统默认算法
sysctl net.ipv4.tcp_congestion_control

# 查看当前系统支持的所有算法
sysctl net.ipv4.tcp_available_congestion_control

# 查看特定连接的算法（需要 root 权限）
ss -ti | grep cubic
```

### 3. BBR 一定比 CUBIC 好吗？

- **BBR 的优势**：基于测量带宽和延迟（不再依赖丢包），在**高带宽、长距离网络**（如跨国专线）下能极大榨干带宽、降低延迟。
- **BBR 的风险**：在**浅缓冲区**或与 CUBIC 混合部署的环境中，BBR 可能过于激进，抢占过多带宽，导致 CUBIC 流“饥饿”。
- **建议**：优先在可控内部网络中测试后再切换。

### 4. 为什么 TCP 流量有“锯齿状”波动？

因为拥塞控制是“积极探测 -> 发现丢包 -> 退缩避让 -> 再次探测”的循环过程。CUBIC 通过三次函数让这个波动变得更平滑，但无法消除波动本身。


## 六、常用命令速查（拥塞控制相关）

| 操作 | 命令 |
| :--- | :--- |
| 查看当前 TCP 拥塞控制算法 | `sysctl net.ipv4.tcp_congestion_control` |
| 查看系统支持的算法列表 | `sysctl net.ipv4.tcp_available_congestion_control` |
| 临时切换算法（重启失效） | `sysctl -w net.ipv4.tcp_congestion_control=bbr` |
| 查看特定连接的实时 cwnd / ssthresh | `ss -ti \| grep -E "cwnd\|ssthresh"` |
| 查看当前 BBR 状态（如已启用） | `lsmod \| grep bbr` |
| 查看网络统计信息（含重传、超时） | `netstat -s \| grep -i retrans` |


## 七、核心总结

1. **拥塞控制是 TCP 的“自动油门”**：通过 `cwnd` 动态调节发送速率，核心机制为**慢启动**（指数探路）、**拥塞避免**（线性爬坡）、**快速重传/恢复**（高效纠错）。
2. **CUBIC 是当前的“版本答案”**：采用 **y = x³ 三次函数**，做到“丢包后快速弹回（凹函数）、超过阈值谨慎试探（凸函数）”，大幅提升高带宽网络利用率。
3. **TCP 有感知但无认知**：它能精确测量 RTT 和丢包，但不知道为什么丢包，也绝不会自己换算法。
4. **拥塞控制 ≠ MTU 调整**：一个管“数量”（发多少包），一个管“尺寸”（包多大），不可混为一谈。
5. **调优需谨慎**：BBR 虽强但可能影响公平性，生产环境切换前务必压测。

> **核心原则**：
> 多卡训练（或任何高性能网络应用）的性能不仅取决于带宽，更取决于拥塞控制算法与网络环境的匹配度。应结合 **网络延迟 + 丢包率 + 算法特性** 进行综合调优，才能榨干硬件性能。

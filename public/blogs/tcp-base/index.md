
## 一、TCP 三次握手（Three-Way Handshake）

TCP 三次握手是建立可靠连接的基础，核心目的是**同步双方的初始序列号（SEQ）**，并协商连接参数。

### 1. 握手过程详解

| 步骤 | 发起方 | 动作 (报文) | 关键作用 | 状态变化 |
| :--- | :--- | :--- | :--- | :--- |
| **第一次握手** | 客户端 | 发送 **SYN** 报文（SEQ=x） | 客户端请求建立连接，告知服务端自己的初始序列号 x | `CLOSED` → `SYN_SENT` |
| **第二次握手** | 服务端 | 回复 **SYN+ACK** 报文（SEQ=y, ACK=x+1） | 服务端确认收到 SYN，告知客户端自己的初始序列号 y | `LISTEN` → `SYN_RCVD` |
| **第三次握手** | 客户端 | 发送 **ACK** 报文（SEQ=x+1, ACK=y+1） | 客户端确认收到 SYN+ACK，连接正式建立 | `SYN_SENT` → `ESTABLISHED` |

服务端收到第三次握手的 ACK 后，状态从 `SYN_RCVD` 变为 `ESTABLISHED`。

### 2. 状态变迁图

```text
  客户端 (主动打开)                       服务端 (被动打开)
  ================                        ================

     CLOSED                                   LISTEN
       |                                        |
       |  (1) 发送 SYN (SEQ=x)                  |
       |--------------------------------------->|  收到 SYN
       |                                        |
    SYN_SENT                                 SYN_RCVD
       |                                        |
       |  (2) 收到 SYN+ACK (SEQ=y, ACK=x+1)    |
       |<---------------------------------------|  发送 SYN+ACK
       |                                        |
   (发送 ACK)                                   |
       |  (3) 发送 ACK (SEQ=x+1, ACK=y+1)      |
       |--------------------------------------->|  收到 ACK
       |                                        |
   ESTABLISHED                              ESTABLISHED
   (可以发送数据)                            (可以发送数据)
```

### 3. 为什么是三次不是两次或四次？

- **不是两次**：两次握手无法防止**历史连接请求**的干扰。第三次握手的作用是客户端通过 ACK 确认这是当前有效的请求，避免服务端为过期 SYN 分配资源。
- **不是四次**：三次已足够完成核心任务——同步双方初始序列号并确认收发能力。第二步中服务端将 SYN 和 ACK 合并发送，效率更高。

### 4. SYN 洪水攻击

- **原理**：攻击者伪造大量 IP 发送 SYN，服务端回复 SYN+ACK 后永远等不到第三次 ACK，导致大量连接卡在 `SYN_RCVD`，占满连接队列。
- **防御**：现代操作系统通过 **SYN Cookie** 技术防御——收到 SYN 时不分配资源，而是计算 cookie 作为 SEQ 返回，只有收到正确 ACK 后才分配资源。


## 二、TCP 四次挥手（Four-Way Handshake）

TCP 四次挥手用于**优雅地关闭连接**。由于 TCP 是全双工的，每个方向都需要单独关闭，因此需要四次。

### 1. 挥手过程详解

假设客户端主动关闭，服务端被动关闭。

| 步骤 | 发起方 | 动作 (报文) | 关键作用 | 发起方状态变化 | 接收方状态变化 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **第一次挥手** | 客户端 | 发送 **FIN** 报文 | 客户端告知服务端数据已发完，请求关闭 | `ESTABLISHED` → `FIN_WAIT_1` | `ESTABLISHED` → `CLOSE_WAIT` |
| **第二次挥手** | 服务端 | 回复 **ACK** 报文 | 服务端确认收到关闭请求，但可能还有数据要发 | `FIN_WAIT_1` → `FIN_WAIT_2` | `CLOSE_WAIT` |
| **第三次挥手** | 服务端 | 发送 **FIN** 报文 | 服务端数据发完，请求关闭 | `FIN_WAIT_2` → `TIME_WAIT` | `CLOSE_WAIT` → `LAST_ACK` |
| **第四次挥手** | 客户端 | 回复 **ACK** 报文 | 客户端确认收到 FIN，进入 TIME_WAIT | `TIME_WAIT` → (2MSL后) `CLOSED` | `LAST_ACK` → `CLOSED` |

### 2. 状态变迁图

```text
  客户端 (主动关闭方)                       服务端 (被动关闭方)
  ================                        ================

  ESTABLISHED                             ESTABLISHED
  (正在传输数据)                           (正在传输数据)
       |                                        |
       |  (1) 发送 FIN                         |
       |--------------------------------------->|  收到 FIN
       |                                        |
  FIN_WAIT_1                               CLOSE_WAIT
       |                                        |
       |  (2) 收到 ACK                          |  (服务端此时可以继续发数据)
       |<---------------------------------------|
       |                                        |
  FIN_WAIT_2                              (服务端发完剩余数据)
       |                                        |
       |  (3) 收到 FIN                         |
       |<---------------------------------------|  (服务端发起关闭)
       |                                        |
  TIME_WAIT                                LAST_ACK
  (等待 2MSL)                                  |
       |  (4) 发送 ACK                         |
       |--------------------------------------->|  收到 ACK
       |                                        |
       |                                    CLOSED
  (2MSL 超时)
       |
  CLOSED
```

### 3. 为什么是四次不是三次？

- 客户端发 FIN 只代表自己不发数据，不代表服务端数据已发完。
- 服务端需要先回复 ACK（告知已收到关闭请求），待自己剩余数据发完后，再发送 FIN。
- 因此 ACK 和 FIN 无法合并，必须分两步，总共四次。

### 4. 为什么客户端要等待 2MSL（TIME_WAIT）？

1. **确保最后一个 ACK 能到达服务端**：若 ACK 丢失，服务端会重发 FIN，客户端需在 TIME_WAIT 状态下能收到并重发 ACK。
2. **让网络中所有迷路报文过期消失**：2MSL 确保本次连接的所有报文从网络中消失，不干扰后续使用相同 IP 和端口的新连接。

### 5. 快速记忆口诀

> **主动关，FIN_WAIT 走两步；被动关，CLOSE_WAIT 等数据。**
> **最后 ACK 不能丢，TIME_WAIT 守两秒（指 2MSL）。**


## 三、TCP 大包拆分机制（Segmentation）

TCP 在发送大块数据时，会根据网络链路的最大传输单元进行拆分，这个过程称为 **TCP 分段（Segmentation）**。

### 1. 为什么要拆分？

- 以太网最常见的 **MTU（最大传输单元）** 是 **1500 字节**。
- 数据包超过 MTU 则无法在一个网络帧中传输，必须拆分。

### 2. 拆分依据：MSS（最大分段大小）

- **MSS = MTU - IP首部(20字节) - TCP首部(20字节)**
- 标准以太网下：**MSS = 1500 - 20 - 20 = 1460 字节**
- TCP 在三次握手时协商 MSS，确保每个 IP 包总长度 ≤ MTU。

### 3. 完整传输过程图解

以发送 8000 字节数据为例：

```text
应用层 (你的程序)
   |  发送 8000 字节数据
   v
TCP 层 (分段)
   |  根据 MSS=1460，将数据切分为 6 个段：
   |  Segment 1 (1460字节)  -> 封装 TCP头 + IP头 (总长1500)
   |  Segment 2 (1460字节)  -> 封装 TCP头 + IP头 (总长1500)
   |  Segment 3 (1460字节)  -> 封装 TCP头 + IP头 (总长1500)
   |  Segment 4 (1460字节)  -> 封装 TCP头 + IP头 (总长1500)
   |  Segment 5 (1460字节)  -> 封装 TCP头 + IP头 (总长1500)
   |  Segment 6 (700字节)   -> 封装 TCP头 + IP头 (总长740)
   v
IP 层 (路由和发送)
   |  每个包都小于1500，IP层直接发送，无需分片
   v
网络传输
   v
接收端 TCP 层 (重组)
   |  根据 SEQ 号（1, 1461, 2921, ...）将段排序重组
   v
应用层 (你的程序)
   |  得到完整的 8000 字节数据
```

### 4. IP 分片（Fragmentation）的危害

如果 IP 层被迫分片（如中间路由器 MTU 更小）：

- **只要丢失一个 IP 分片，整个原始数据包就必须全部重传**。
- IP 层本身无重传机制，依赖 TCP 发现丢包并重传整个大包，效率极低。

### 5. 应用层拆包/粘包问题

- **现象**：发送两次数据，接收方可能一次读完（粘包），或一个大包只读到一半（拆包）。
- **原因**：TCP 是**流式协议**，只保证字节顺序，不保护应用层消息边界。
- **解决方案**：必须在应用层协议中解决，常见方案：
  1. **固定长度**：每个报文固定大小
  2. **分隔符**：如使用换行符 `\n`
  3. **长度字段**：在报文头部用 4 字节标识整个报文长度（最通用）

### 6. 核心概念对比表

| 概念 | 发生层级 | 拆分单位 | 谁负责重组 | 后果 |
| :--- | :--- | :--- | :--- | :--- |
| **TCP 分段** | 传输层 (TCP) | 数据流 → 多个 Segment | 接收端 TCP 层 | **高效**。丢失一段只重传这一段 |
| **IP 分片** | 网络层 (IP) | 单个 IP 包 → 多个 Fragment | 接收端 IP 层 | **低效**。丢失任意一片，整个包全丢 |
| **应用层拆/粘包** | 应用层 | 业务消息 → 字节流 | 开发者写的代码 | 需通过协议（如长度前缀）解决边界 |


## 四、TCP 协商能否完全规避 IP 分片？

**核心结论：TCP 的 MSS 协商可以"极大程度地规避"IP 分片，但在某些特殊网络路径下，无法做到 100% 绝对规避。**

### 1. TCP 协商规避了什么？（解决了 95% 的问题）

- TCP 三次握手时协商 MSS，取双方较小值作为本次连接的传输上限。
- 此后 TCP 层严格按照 MSS 切分数据，每个发出网卡的 IP 包总长度 ≤ MTU。
- 在正常网络传输中，中间路由器没有理由再对包进行 IP 分片。

### 2. 什么情况下依然会发生 IP 分片？（那 5% 的漏网之鱼）

| 场景 | 原因 | 后果 |
| :--- | :--- | :--- |
| **路径 MTU 小于协商值** | 中间路由器 MTU 更小（如 PPPoE 1492、VPN 1400），且 ICMP 差错报文被防火墙拦截 | 大包被丢弃，发送端收不到通知，造成"黑洞"现象 |
| **IP/TCP 头带额外选项** | 启用 Timestamp、SACK 等扩展，TCP 头膨胀到 40+ 字节 | IP头(20)+TCP头(40)+数据(1460)=1520 > 1500，被迫分片 |
| **UDP 或 DDoS 流量** | UDP 无 MSS 协商机制，应用层直接发送大数据包 | IP 层必须分片 |

### 3. 现代操作系统的硬规避方案

Linux 内核参数 **`tcp_mtu_probing`** 可主动探测路径 MTU：

- 若发现发送包大于 PMTU，内核会强制将数据段再切小（如从 1460 降到 1440）
- 确保即使加上 TCP 选项，总包长也 ≤ 路径 MTU

### 4. 核心结论

> **TCP 的 MSS 协商是为了"避免"IP 分片，但无法"消灭"IP 分片。**
>
> 1. **在直连网络或标准以太网环境下**：MSS 协商有效，基本不会发生 IP 分片。
> 2. **在跨运营商、VPN 或隧道环境**：由于路径 MTU 未知，依旧可能发生分片或丢包，此时依赖 **PMTUD（路径 MTU 发现）** 来动态调整。
> 3. **终极手段**：在服务端抓包时，如果发现大量 IP 分片（`ip.flags.mf == 1` 或 `frag_offset > 0`），通常意味着 MTU 协商失败（ICMP 被屏蔽）或网卡 TSO 驱动 bug。


## 五、常用命令速查（网络相关）

| 操作 | 命令 |
| :--- | :--- |
| 查看本机网卡 MTU | `ifconfig` 或 `ip link show` |
| 查看 TCP 连接状态统计 | `netstat -nat | awk '{print $6}' | sort | uniq -c` |
| 查看 TIME_WAIT 数量 | `ss -tan | grep TIME-WAIT | wc -l` |
| 抓包分析 TCP 握手/挥手 | `tcpdump -i eth0 -nn 'tcp[tcpflags] & (tcp-syn|tcp-fin) != 0'` |
| 抓包查看 IP 分片 | `tcpdump -i eth0 -nn 'ip[6:2] & 0x1fff != 0 or ip[6] & 0x20 != 0'` |
| 查看路径 MTU（Linux） | `tracepath <目标IP>` |
| 查看当前系统 TCP 内核参数 | `sysctl -a | grep tcp` |


## 六、常见问题排查

### 1. 为什么第三次握手的 ACK 丢了？

- 服务端收不到 ACK，会保持在 `SYN_RCVD` 状态，并超时重传 SYN+ACK。
- 客户端收到重传的 SYN+ACK 后会重新发送 ACK。
- 若重传次数达到上限，服务端会关闭该半连接。

### 2. TIME_WAIT 过多怎么办？

- `TIME_WAIT` 是主动关闭方正常状态，等待 2MSL（通常 60 秒）。
- 过高时可能导致端口耗尽，可调整内核参数：
  - `net.ipv4.tcp_tw_reuse = 1`（允许重用 TIME_WAIT 连接）
  - `net.ipv4.tcp_tw_recycle = 1`（快速回收，但 NAT 环境下慎用）
  - 调整 `net.ipv4.ip_local_port_range` 扩大端口范围

### 3. 如何判断当前连接是否发生了 IP 分片？

- 在发送端或接收端抓包，过滤 `ip.flags.mf == 1` 或 `frag_offset > 0`。
- 若出现大量分片包，说明 MTU 协商或路径发现存在问题，可尝试手动降低 MSS。


## 七、核心总结

TCP 网络通信的核心机制贯穿连接的整个生命周期：

1. **三次握手**：建立连接，同步序列号，协商 MSS 等参数。
2. **数据传输**：通过 MSS 控制分段大小，避免 IP 分片，提升传输效率。
3. **四次挥手**：优雅关闭连接，TIME_WAIT 保证最后一个 ACK 可靠送达。

在日常开发与运维中，以下几点尤为重要：

- **抓包分析**是排查网络问题的首要手段，熟悉 `tcpdump` 和 Wireshark 过滤语法。
- **MTU/MSS 协商**直接影响传输效率，跨网络环境时需关注路径 MTU 是否一致。
- **TIME_WAIT 状态**需合理监控和调优，避免端口耗尽。
- **应用层拆包/粘包**必须在协议设计层面解决，不能依赖 TCP 底层。

> **核心原则：**
>
> 网络通信的性能和稳定性，取决于对 TCP 各阶段机制的深入理解与合理配置。
>
> 应从 **连接建立 → 数据传输 → 连接关闭** 全链路进行综合分析和优化。
